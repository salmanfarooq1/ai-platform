# ADR 0008: The event bus and CloudEvents

**Status:** Accepted

## Context
Strict rule 9 asks for open standards, CloudEvents among them. Later sprints need to react to what the platform did: durable jobs and an outbox (Sprint 007), trust and receipts (008), and a Kafka adapter (010). Today the gateway writes one `gateway_decisions` row per call and tells nobody.

## Decision
- **A port.** `EventBus.publish(event, *, tx=None)` and `subscribe(type, handler)` in `ports/events.py`. A handler is `async def handler(event, tx)`. `"*"` subscribes to every type.
- **Events are CloudEvents 1.0.** `CloudEvent` is a frozen dataclass with `id`, `source`, `type`, `specversion` (only `1.0` is accepted), `time` (UTC), `subject`, `datacontenttype` and `data`, plus the extension attribute `tenantid`. `to_dict()` gives the JSON structured form. Type names are `platform.<area>.<thing>.v<major>`, so a breaking change to a payload is a new type.
- **The default adapter is in-process** (`adapters/inprocess_events.py`). `publish` awaits each handler in the publisher's task, in subscription order. It passes `tx` through, so a handler runs in the transaction context the caller gives. A handler that raises is logged and skipped: the other handlers still run, and the publisher is not failed by a subscriber.
- **The gateway publishes `platform.gateway.decision.v1`** after each decision row is written, inside the same transaction (`gateway/record.py` passes the connection as `tx`). `subject` is the decision id. `data` is `decision_id`, `outcome`, `stage`, `reason`, `action`, `resource`, `request_id` and `execution_id`. It never carries input text, and not the input hash either; a subscriber that needs more reads the decision row under row-level security.
- **A bus may fail the publisher.** An adapter that must not lose an event (the outbox in 007) raises from `publish`. Because the publish happens inside the record's transaction, the row is rolled back and `enforce()` turns an allow into a deny `decision_unrecorded` (503). A bus that fails therefore cannot let an action through unrecorded (strict rule 3). **A decision row is never lost because of the bus.** For a deny, the publish runs in a savepoint (`gateway/record.py`). If the bus raises, only the publish is rolled back. The deny row is committed, the error is logged and the call stays denied.
- **Contract.** `tests/contracts/test_event_bus_contract.py` runs against every adapter (type filtering, wildcard, order, `tx` pass-through, failure isolation, CloudEvent validity). The outbox and the Kafka adapter must pass it.

## Consequences
- Subscribers can be added without touching the gateway. The first real subscribers arrive in Sprint 007.
- Every governed call pays for the handlers it has, inside the request. The default bus has none.
- A subscriber that writes to the database through `tx` and fails with a database error aborts the decision's transaction, which fails closed. Subscribers should not do that unless they mean to be part of the record.
- Delivery with the in-process bus is at most once and only while the process lives. At-least-once delivery is the outbox's job.

## Alternatives considered
- **Publish after the commit:** a crash between the commit and the publish loses the event, which is what the outbox pattern exists to avoid. Publishing inside the transaction lets an outbox adapter commit with the decision.
- **A custom event format:** rejected for rule 9.
- **Putting the input hash in the payload:** rejected. A hash of a short input can be guessed, and subscribers do not need it.

## Outbox (Sprint 007)
The in-process bus delivers at most once. Sprint 007 adds the transactional outbox, which is the default adapter now (`EVENT_BUS=outbox`; `inprocess` is still available).
- **Write with the change.** `OutboxEventBus.publish(event, tx=conn)` inserts the event into the `outbox` table on the caller's connection (`adapters/pg_outbox_events.py`). It commits or rolls back with the state change that made it: a decision row, or a job marked succeeded. A rolled-back transaction leaves no event. With no `tx` the event gets a transaction of its own. The same event id twice is stored once (unique on tenant and event id).
- **Subscribers still run inline.** After the write, `subscribe`d handlers run in the publisher's task and get `tx`, as before. They are for work that must commit with the change. The bus passes the same contract suite as the other adapters.
- **A failed write fails the publisher.** The gateway rule is unchanged (M1): an allow whose outbox write fails is denied with 503 `decision_unrecorded` and its row rolls back. A deny publishes in a savepoint and keeps its row.
- **The relay publishes the rows** (`OutboxRelay`, run by `python -m workers` or by the API with `EMBEDDED_RELAY=true`). It lists unpublished rows, locks one (`FOR UPDATE SKIP LOCKED`), publishes it to a target `EventBus`, and marks it sent in the same transaction. The target is the in-process bus today and the Kafka adapter in Sprint 010. Several relays can run at once.
- **At least once.** A crash after the target got the event and before the mark commits sends it again. A failed send is counted (`attempts`) and tried on the next pass. After `OUTBOX_MAX_ATTEMPTS` the row is left for an operator.
- **Consumers dedupe by CloudEvent id.** `IdempotentConsumer` wraps a handler: an LRU stops repeats in one process, and the `processed_events` table (per tenant and consumer) stops them across restarts. The id and the handler's own writes share a savepoint, so a handler that raises records nothing.
- **Events written so far:** `platform.gateway.decision.v1` (every decision) and `platform.ingest.completed.v1` (a finished ingest job: ids, hash, status and chunk count, no text).
- **Workers and the relay are not tenants.** They find rows through three narrow SECURITY DEFINER functions (`jobs_claim`, `jobs_tenant_of_execution`, `outbox_pending`) that return only ids and tenants. Everything else runs under `tenant_connection` as `gap_app`. See ADR-0011.
- **Cost.** Every decision now writes one more row. There is no retention yet (Sprint 008): `outbox` and `processed_events` grow.

## Kafka (Sprint 010)
`EVENT_BUS=kafka` publishes the outbox to Kafka. `outbox` stays the default, and nothing changes for anyone who does not set it.
- **Where Kafka is reached.** Only by the relay. With `EVENT_BUS=kafka` the API still builds the outbox bus, so a decision row and its event commit in one transaction and a Kafka outage cannot stop or lose a decision. `workers.context.make_relay` gives the relay a `KafkaEventBus` as its target. A decision is never denied because Kafka is down. The event waits in the outbox.
- **Adapter.** `adapters/kafka_event_bus.py`, on `aiokafka` (Apache-2.0, pinned `==0.14.0`). It is the only module that imports it (import-lint test). The client sits behind two small protocols, so the adapter's logic runs in tests on an in-memory broker.
- **Topic and key.** Topic `platform.<type without its version>`: `platform.gateway.decision.v1` goes to `platform.gateway.decision`. The key is the tenant id. A key always maps to one partition, so a tenant's events keep their order. There is no order across tenants. A new major version of a type is a new topic, as it is a new type.
- **CloudEvents binary mode.** The attributes are `ce_specversion`, `ce_id`, `ce_source`, `ce_type`, `ce_time`, `ce_subject` (when set) and the extension `ce_tenantid`, with `content-type` for the data content type. The value is the JSON `data`. It carries no input text, as before.
- **Producer.** `acks=all` and an idempotent producer. `publish` returns when the broker acknowledged the record, and raises when it did not, so the relay keeps the row and counts the attempt. The send is bounded by `KAFKA_SEND_TIMEOUT_SECONDS` (15) and each request by `KAFKA_REQUEST_TIMEOUT_SECONDS` (10), because the relay holds a row lock while it waits. Delivery stays at least once: a relay that dies after Kafka acknowledged and before the row is marked sends it again.
- **Consumer.** `KafkaEventBus.consume(type, handler, name=...)` registers a handler of the consumer group `KAFKA_GROUP_ID`. `poll_once` and `run` read a record, decode it and run the handlers inside `IdempotentConsumer`. With a pool, `processed_events` (from migration `0008`) stops a repeat: the CloudEvent id and the handler's own writes share one savepoint. Auto-commit is off. The offset is committed only after every handler succeeded. A record that was read and not committed is delivered again after a restart, and the dedupe makes that safe.
- **Dead-letter topic.** A handler that raises is tried `KAFKA_MAX_ATTEMPTS` times (5 by default, with `KAFKA_RETRY_BACKOFF_SECONDS` between tries). Then the record is copied to `<topic>.dlq` with its own headers and `x-error` (the exception class only), `x-error-code` (`handler_failed` or `decode_failed`), `x-attempts`, `x-original-topic`, `x-original-partition`, `x-original-offset` and `x-group-id`, and the offset is committed. One poison message does not block its partition. The exception message is never put in a header or a log, because it may hold input text or a secret. If the dead-letter send or the commit fails, the consumer seeks the partition back to that record before the next poll, so the next record's commit cannot cover it and the record is read again (QA H1). A record that is not a CloudEvent (a missing header, bad JSON) goes there at once with `x-attempts=1`, because trying it again cannot help. A restart during the retries restarts the count.
- **Order relies on sequential sends.** The relay sends one row at a time and waits for each acknowledgement. For one tenant it stops at the first row that fails or is locked, and the tenant's later rows wait for the next pass (another tenant is not held up). A row that has used all `OUTBOX_MAX_ATTEMPTS` is left for an operator, and the tenant's later rows then go past it. A send that was applied but whose acknowledgement was lost is sent again, so the topic holds a duplicate. Consumer dedupe absorbs it, and `tests/fake_kafka.py` can model it (`lost_acks`). Do not make the producer send concurrently without changing this.
- **In-process subscribers.** `subscribe` keeps the port's meaning: handlers run in the publisher's task right after the send, with the caller's `tx`. That is what lets the bus pass the same contract suite as the other adapters. Work that must survive a crash uses `consume`.
- **The `*` wildcard on `consume`** covers the three platform types in `ports/events.py` and any type named in another `consume` call. A Kafka topic list is fixed when the consumer starts, so a type the platform has not defined is not seen through `*`.
- **Settings.** `KAFKA_BOOTSTRAP` (required with `EVENT_BUS=kafka`), `KAFKA_CLIENT_ID`, `KAFKA_GROUP_ID`, `KAFKA_SECURITY_PROTOCOL` (`PLAINTEXT`, `SSL`, `SASL_PLAINTEXT`, `SASL_SSL`), `KAFKA_SASL_MECHANISM` (`PLAIN`, `SCRAM-SHA-256`, `SCRAM-SHA-512`), `KAFKA_SASL_USERNAME`, `KAFKA_SASL_PASSWORD`, `KAFKA_MAX_ATTEMPTS`, `KAFKA_RETRY_BACKOFF_SECONDS`. SASL values come from the environment only. The password is a `SecretStr`, it is unwrapped in one place (`KafkaConfig.client_options`), and a settings error names the variable and not its value.
- **Switching back.** No migration. Rows written under `kafka` are ordinary outbox rows. With `EVENT_BUS=outbox` the same relay sends the unsent ones to the in-process bus. Rows already sent to Kafka stay sent. Nothing is replayed in either direction.
- **Compose and tests.** The `streams` profile runs one Apache Kafka node (`apache/kafka:4.3.1`) and a job that creates the topics and their dead-letter topics with 3 partitions. The EventBus contract suite runs against the adapter on `tests/fake_kafka.py` in the normal suite. The fake models partitions by murmur2 key hash, offsets, a committed offset per group, redelivery of a record read and not committed, and an acknowledgement after the append. It is a model, not a recording. The live run checks redelivery more weakly than the fake: it replays through a new group that reads from the start, because the test cannot reset a real group's offset. `scripts/verify/kafka.sh` runs the same tests on a live broker (`KAFKA_LIVE_BOOTSTRAP`). The test id says `kafka-fake` or `kafka-live`. See `docs/operations.md` (the Kafka section).
- **Not done.** No consumer ships with the platform yet: no code subscribes with `consume`. Retention of the topics is the broker's setting. Security of a production cluster (TLS, ACLs) is not verified here.
