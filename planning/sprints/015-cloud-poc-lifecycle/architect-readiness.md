# Sprint 015: Architect readiness

Preparation only. Implementation waits for accepted 011–014 snapshots and the complete sprint contract. The Builder's source map is in `build-log.md`.

## Selected boundaries

- **No implicit cloud spend.** Use the documented generic VM interface and local Compose restore drill until a real provider/account is configured. Mock/local evidence must identify itself. Do not choose a provider, create resources, publish images or use an SSH credential merely because it exists on the machine. Prepare the release/verification workflows; actual human release/cloud execution remains explicitly pending when unavailable.
- **Honest release identities.** A source commit or local Docker tag is not a published GHCR digest. The release job must generate and validate the deployable digest manifest from actual published outputs. A checked-in template cannot be launched until all references resolve to verified immutable artifacts. Preserve upstream source identities/notices when mirroring. Local drills may use captured local image IDs and must say so. Do not reuse the retired historical production Compose file.
- **Previous-release proof.** Select the actual previous tag or the requirements' last merged sprint fallback; preserve its source/image identity. Use only isolated, owned test state for compatibility runs. Do not weaken the current supply-chain gate or claim an unexecuted old-release upgrade passed. The future contract must state how the first local, unlanded sequence supplies its accepted prerequisite snapshot while retaining the human release test.
- **Write-consistent backup.** The platform records decisions even for reads. Pausing ingestion alone cannot produce a consistent DB/object/key set. Quiesce all platform writers, including API decision writes, workers and relays; reject incoming requests during the bounded capture rather than leaving unaudited reads open. Establish one manifest binding schema head, database dumps, object content and key/public-key identities, then resume. Restore into fresh, explicitly owned state and verify object hashes, row counts, chain continuity, old signatures and smoke behavior before switching.
- **Recovery secret survives compute deletion.** A restic password stored only on the VM or inside the backup it encrypts cannot restore a destroyed VM. Before allowing `down`, require a verified private recovery credential outside the resources being destroyed. Keep it out of git, state, logs, command arguments, image contexts and general artifacts; use opaque file/environment references. Retain it through the local drill and test that its loss prevents destructive teardown. Never silently generate a replacement signing key when restoring an existing backup.
- **Explicit ownership and destination.** Every lifecycle command selects an explicit stack. Validate the state/ownership marker and account/host/disk/bucket identities before changes. `down` verifies the new backup and targets only its owned compute/disks; buckets, registry and recovery material remain. A leak report lists observed retained resources; provider estimates are labelled estimates and no invented measured cost is reported. Tests must reject foreign resources, unexpected symlinks, a platform DB used as another restore target, and incomplete backups.
- **Trusted transport and inputs.** SSH uses a verified host key and narrowly scoped credentials. Never disable host-key checking. Validate stack/resource identifiers and structured arguments; do not interpolate untrusted data into shell commands. Generate secrets privately and retain the 013 secret-reference/catalog boundary. The local test adapter does not become a production fake-model switch.
- **Supported command wording.** Use `poc showcase`, matching the repository wording rule. Require the stack argument for `up`, `seed`, `showcase`, `backup` and `down`; do not infer the target of a destructive command from an ambient default.
